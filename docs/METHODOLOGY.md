# 方法论与已知偏差

这份文档说明 indie-ledger 的数据是怎么来的、它能回答什么、不能回答什么。

**规则版本**：`2026-11-09`
**数据窗口**：2024-01-01 → 2026-11-09

---

## 1. 总体范围（population）

> **本数据集覆盖的是「在 Show HN 发帖并链接自己产品的开发者」，去重后按产品计。**
> 它不覆盖全部独立开发者。

这不是免责声明，是使用说明。任何从本数据得出的结论都必须带着这句话一起传播。

### 这个样本的系统性偏差

| 偏差 | 方向 | 说明 |
|---|---|---|
| 公开构建倾向 | 高估存活率 | 在 Show HN 发帖的人更可能公开代码，公开代码更容易被 GitHub 侧判定覆盖 |
| 英语使用者 | 高估西方市场代表性 | Show HN 是英语社区，非英语独立开发者几乎不在样本里 |
| 愿意自我宣传 | 高估产品发布意愿 | 安静做完不上报的人完全不在样本里 |
| 域名型工具 | 低估 | 闭源 SaaS 没有 GitHub 仓库，只能靠域名信号，覆盖率低 |
| 2026 年样本 | 严重右删失 | 2026 年上线的产品平均只存活了几个月，还来不及死 |

最后一条尤其重要：**横向比较不同年份的存活率是错的**。2026 年队列的低死亡率不说明它更健康，只说明它还年轻。纵向看同一个队列随时间的变化才有意义。

---

## 2. 数据采集

### 2.1 Show HN（发现层）

- **来源**：Hacker News Algolia 搜索 API，`tags=show_hn`
- **窗口**：2024-01-01 → 2026-11-09，1,044 个 UTC 日
- **粒度**：逐日切片，每天最多 3 次请求
- **原始量**：88,874 条帖子

**为什么必须逐日切片**：Algolia 单次查询的可触及上限是 1000 条。按年查询会报告 `nbHits=28,246`，但实际只能取到最新的 1000 条，之后页码返回 `nbHits=0`。**96% 的数据静默丢失，没有任何报错。**

**为什么必须双边日期过滤**：只给下界 `created_at_i>{lo}` 时，上界被忽略，返回整个语料库（507,043 条），而不是请求的时间段。

### 2.2 主机分类

原始帖子按链接类型分类，**只有 `product_site` 和 `github` 进入台账**：

```
platform        google.com, huggingface.co, apple.com, npmjs.com, ...   2%
hosting         *.vercel.app, *.workers.dev, blogspot.com, itch.io, ...   5%
content_host    medium.com, substack.com, dev.to, hashnode.dev            0.2%
github          github.com/<owner>/<repo>                          31%
product_site    everything else                                    55%
```

不剔除的话，`google.com` 在 14 天样本里就出现 23 次——台账一半是平台不是产品。

## 3. 存活判定

### 3.1 置信度分层

**不同证据强度的结论永远不混在同一张表里。** 报告里每张表的分母互不相同，不能相加，也不能互相印证。

| 层 | 证据 | 强度 | 覆盖 |
|---|---|---|---|
| **high** | GitHub 仓库状态 | 无歧义 | 24,767 个仓库 |
| **medium** | DNS + HTTP | 可确认站点消失，无法区分「死掉」与「搬家」 | 36,881 个域名 |
| **none** | 无信号 | — | 计入 `unverified`，不参与任何比率 |

### 3.2 GitHub 侧（高置信）

| 信号 | 判定 |
|---|---|
| 仓库 404 / 删除 | `dead` |
| `archived = true` | `dead` |
| `pushed_at` 超过 365 天 | `dormant` |
| `pushed_at` 180–365 天 | `slowing` |
| `pushed_at` 180 天内 | `active` |

仓库删除和归档是**无歧义的**——没有歧义空间，这是这层能做主结论的原因。

### 3.3 域名侧（中置信）

规则顺序本身就是设计的一部分，顺序错了结果就错：

```
1. NXDOMAIN 二次确认（间隔约 1 秒）           -> dead
2. 80 或 443 任一端口返回 HTTP < 400           -> alive
3. HTTP 403 / 405 / 429                       -> blocked  （站点在，只是拒绝爬虫）
4. DNS 可解析 + 端口开放但请求异常              -> degraded （主机在，服务异常）
5. DNS 可解析 + 无监听                         -> dead
```

**最关键的一条：TLS 证书错误不是死亡。** 证书过期只说明证书烂了，站点还活着。

初版规则用「HTTPS 失败 ⇒ 已死」，在 40 个域名上复核发现 6/13 是误判：证书过期、自签证书、站点屏蔽 HEAD 请求、403 限流。修正后死亡率从 32% 降到 13%，且 13% 里 7/9 经二次独立核验确认为真死。

## 4. 这份数据不回答什么

1. **不回答**「独立开发者整体的失败率」—— 样本是 Show HN 发帖者，不是开发者总体。
2. **不回答**产品失败的原因—— 台账只记录状态，不推测动机。
3. **不回答**收入与转化—— 台账不含任何营收数据。
4. **不区分**「主动完成」与「被放弃」—— 两者都在「不再维护」里。
5. **未覆盖**未在 Show HN 发帖的产品—— 这恰恰是最大的一块空白。

---

## 5. 「不再维护」而不是「失败」

这个措辞不是修辞上的谨慎，是分类上的准确。

一个产品不再更新，可能是失败了，也可能是作者做完了、赚够了、换赛道了。这两种情况在信号上完全一样，混称为「失败」是往数据里塞结论。

---

## 6. 可复现性

| 保证 | 实现 |
|---|---|
| 每个数字可回溯 | 所有统计量都能定位到 `data/ledger.jsonl`、`data/repo_status.jsonl`、`data/liveness.jsonl` 的具体行 |
| 同数据同输出 | 渲染器连续两次渲染字节一致（脚本内置断言，失败即 exit 1） |
| 不在正文写时间戳 | 报告正文无生成时间，只有数据窗口 |
| 采集可续 | 逐日文件 + checkpoint，重复运行不产生重复行 |
| 判定不依赖 LLM | 全部判定由确定性规则产生，不使用模型推断 |

---

## 7. 成本

| 层 | 成本 |
|---|---|
| L1 采集 | 每年历史约 1,100 次请求；此后每天 3 次。无鉴权。 |
| L2a GitHub | 24,767 次检查。无 PAT 约 17 天；有 PAT 约 5 小时。 |
| L2b 域名 | 36,881 个域名 × 约 5 秒（DNS 解析主导）≈ 53 小时，单次遍历，无配额。 |
| L3/L4 | 本地计算。**任何判定都不需要 LLM。** |

没有一层需要付费 API。运营成本主要是 GitHub 配额，PAT 消除了这一项。

---

## 8. 已知待改进项

- 域名扫描实际速率是 11.5 个/分钟，比最初估计的 1.4 秒/个慢一倍多。DNS 解析是瓶颈。下一步应加并发（限制在 8–16 个 worker，避免被 DNS 服务端限流）。
- 域名型产品到 GitHub 仓库的自动匹配率只有 20%（3 种策略在 10 个样本上最好命中 2 个）。闭源产品的覆盖率因此受限。
- 未接入 Product Hunt（官方 GraphQL API 默认禁止商用用途）、Reddit、Indie Hackers（当前返回 403）。
- 未区分「主动完成」与「被放弃」—— 需要 maker 自助纠错机制才能实现。
